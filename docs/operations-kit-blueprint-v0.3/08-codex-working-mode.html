Codex-Regeln

Codex darf keine neue Fachlogik erfinden. Jeder Implementierungsprompt referenziert Prozess, Entität, Status oder UI-Spezifikation aus diesem Blueprint.
RegelBegründung
Roadmap step als erste ZeileKontext sofort klar
Keine Aktionen auf falschen SeitenPage Ownership bleibt stabil
Keine neuen Status ohne Statusmodell-UpdateVermeidet "Procurement in progress" überall
Jede Tabelle: Filter und Detail-LinkExcel-Ablösung
Jede Detailseite: Toolbar obenUI-Konsistenz
Tests vor Final ReportRegressionen verhindern

Blueprint-driven Implementation Rule

Every future Codex implementation step must be traceable to exact Blueprint sections and must finish with a mapping table. If a requested behavior is not in the Blueprint, Codex must either stop and ask for a Blueprint update or explicitly document the gap before coding.

Future prompt must includePurpose
Roadmap stepNames the implementation slice and prevents continuation of stale plans.
Blueprint source filesExact HTML files Codex must inspect before coding.
Exact Blueprint sectionsPage spec, detail wireframe, status model, entity and test scenario references.
Implementation goalSpecific user outcome and page behavior.
Allowed implementation scopeRoutes/helpers/tests/files allowed to change.
Forbidden files/featuresPrevents adjacent ERP feature drift.
Expected files to inspectCurrent app files that implement the area.
Expected UI changesToolbar, tabs, tables, fields, buttons, empty and blocked states.
Expected behavior changesRead/write logic, status derivation, idempotency or no behavior change.
Expected tests/checksTypecheck, lint, build, DB-backed tests, browser retest where relevant.
Browser retest pathExact path a human or browser automation should verify.
Final Blueprint mapping tableBlueprint requirement | Implemented file | Status | Notes.

Before Coding Summary

Before editing files, Codex must summarize:

Required summary itemExample
Which Blueprint sections apply11 Page Specs: Procurement; 15 Detail UI: Purchase Order Detail; 04 Status Models: PO lifecycle.
Which current files implement that areaapp/routes/app.procurement.tsx, app/routes/app.procurement_.$purchaseOrderId.tsx, app/lib/operations-kit.server.ts.
What gap existsPO line value is not shown; duplicate Open Receipt links exist.
How the change will close the gapAdd unit price/value columns and remove duplicate link without changing PO lifecycle logic.

After Coding Summary

After coding, Codex must summarize:

Required summary itemPurpose
What changedConcrete files and UI/behavior changes.
What did not changeExplicitly names forbidden scope that stayed untouched.
Which tests prove complianceAutomated and browser/manual checks tied to Blueprint sections.
What remains inconsistent with the BlueprintKnown gaps and deferred implementation.
Blueprint mapping tableBlueprint requirement | Implemented file | Status | Notes.
